# Decisions log

Short record of what was decided and why. Useful later for report sections 2.1 and 3.2.

| # | Date | Decision | Reason |
|---|---|---|---|
| 1 | 2026-10-19 | C# / .NET 8 | Author is more fluent in C#; official MCP and Anthropic SDKs exist for it. Only the SWE-bench evaluator is Python (CLI). |
| 2 | 2026-10-19 | Claude Haiku 5.5, ~$100 budget (ceiling $150-200) | Cheapest current Claude model; $0.10 / $0.50 per M tokens (to verify). |
| 3 | 2026-10-19 | Custom orchestration, no framework | Frameworks add hidden prompts and calls, which would contaminate cost attribution (RQ2) and the fairness of the comparison. |
| 4 | 2026-10-19 | One agent loop for all configs; topologies only change prompts, tools and wiring | Only the architecture may differ between runs. |
| 5 | 2026-10-19 | Shared context cap of ~80k prompt tokens, identical compaction for all systems | Haiku 5.5 bills a request at 5x above 100k prompt tokens; the cap keeps that from becoming a confound. |
| 6 | 2026-10-19 | One budget per run, shared by all agents | A multi-agent system spends from the same pot as a single agent ("same budget" protocol). |
| 7 | 2026-10-19 | Messages API over plain `HttpClient` behind `IModelClient` (not the `Anthropic` NuGet SDK, for now) | Exact control of usage fields incl. cache tokens; no preview dependency; testable offline. The SDK can be swapped in behind the same interface. |
| 8 | 2026-10-19 | Topologies: hub-and-spoke, coder-reviewer, sequential (last, optional) | Chosen by the author; sequential is dropped first if the schedule slips. |
| 9 | 2026-10-19 | Tool-exposure ablation (full vs. role-restricted tools) on hub-and-spoke | Shows how much of the MCP cost is a tool-design effect (H2). |
| 10 | 2026-10-19 | Task structure labeled from SWE-bench gold patches, plus a small synthetic suite | Realistic main result with a cleaner sanity check (RQ3). |
| 11 | 2026-10-19 | Six tools defined once in `ToolCatalog`; the direct host and the future MCP server both use them | Any cost difference between config A and B must come from MCP, not from different tool text or behaviour. |
| 12 | 2026-10-19 | Tool descriptions kept short | They are sent on every request; their size is part of the MCP-layer cost that RQ2 measures. |
| 13 | 2026-10-19 | `edit_file` is done as exact-match replace (must match once), implemented in C# not in the shell | Same match rules everywhere; preserves line endings and missing final newlines; clear errors help the model retry. |
| 14 | 2026-10-19 | Task containers run with `--network none`, memory and CPU limits, removed afterwards | The isolation the report promises for MCP tools; also keeps runs from affecting each other. |
| 15 | 2026-10-19 | Commands run under the container's own `timeout` (exit 124) | Killing `docker exec` locally does not stop the process inside the container; a hung test would distort later timings. |
| 16 | 2026-10-19 | Non-zero exit codes are normal tool output, not tool errors | Failing tests are information for the agent; `IsError` is reserved for bad arguments, missing files and timeouts. |
| 17 | 2026-10-27 | Every configuration implements `ISystem`; the orchestrator is the same for all | Configs C-E (several agent loops) and B (MCP tools) plug in without touching the run pipeline, the logging or the evaluation. |
| 18 | 2026-10-27 | Prompts are embedded markdown files; their hashes (CRLF-normalized) go into every manifest | One prompt text for all configs, and any change is visible afterwards. Hashing ignores line endings because git on Windows may check files out with CRLF. |
| 19 | 2026-10-27 | The agent sees only the issue text. FAIL_TO_PASS tests and the reference patch are never shown | They are hidden by design in SWE-bench; showing them would invalidate the resolve rate. A test checks it. |
| 20 | 2026-10-27 | Each run starts a fresh container and verifies it: repo at the base commit, clean tree, python works | The patch must contain only what the agent wrote; a wrong prelude fails in seconds instead of after paying for a run. |
| 21 | 2026-10-27 | A run is `completed` when the agent stopped for any reason (done, budget, turns, context); `error` only for infrastructure failures, which are retried | Budget and turn exhaustion are results of the experiment (unresolved), whereas a Docker failure is not and must not count against a configuration. |
| 22 | 2026-10-27 | One predictions file per configuration and repeat; evaluator output is read in two known layouts | The evaluator wants one prediction per instance. Its exact output layout is unconfirmed, so both are parsed. |
| 23 | 2026-10-27 | `batch` skips finished runs and stops at `--max-usd` per session; 3 consecutive infrastructure errors abort | Safe to interrupt and resume; a broken setup cannot silently burn the budget. |
| 24 | 2026-10-27 | `run --dry` drives the real container and tools with a scripted model | Lets the PC setup be verified at zero API cost before the first paid run. |
| 25 | 2026-10-27 | Default per-run limits: 80k prompt tokens, 3M total tokens, $0.50, 50 turns (PLACEHOLDERS) | To be replaced by values calibrated in the pilot; whatever is chosen applies identically to every configuration. |
| 26 | 2026-10-27 | Hub-and-spoke (config C): the orchestrator calls `delegate_task` with a LIST of tasks; one call starts up to N workers with `Task.WhenAll` | `AgentLoop` runs tool calls one by one for reproducibility, so parallelism has to live inside one tool call. N is the maximum per call (2, 3, 4 for the H2 scaling test). |
| 27 | 2026-10-27 | `delegate_task` is a topology tool handled in-process, not part of `ToolCatalog` | It is agent-layer cost, not MCP-layer cost, in the RQ2 attribution. The six catalog tools stay identical across configs. |
| 28 | 2026-10-27 | Each worker is a fresh `AgentLoop` with its own context; it receives the issue text plus its sub-task, and only a short summary (max 2000 chars) goes back | Context isolation is the supposed benefit of multi-agent (model M3); passing the issue costs N copies of it, which is part of the coordination cost being measured. |
| 29 | 2026-10-27 | Workers share one container and one checkout; optional per-task file scopes must be disjoint (checked at delegation) and are enforced on `edit_file`/`write_file` only | Keeps parallel edits from colliding. Scope rejections are ordinary tool errors and show up in the log. Shared checkout and concurrent test runs remain a threat to validity. |
| 30 | 2026-10-27 | Per-agent turn cap equals the single-agent cap (`--max-turns`); the binding limit is the shared run budget | Same budget for every config (decision 6). Reported `turns` for config C is orchestrator plus all workers. |
| 31 | 2026-10-27 | Tool exposure: `full` = all six tools for every agent; `role` = orchestrator read_file, list_dir, run_tests (+ delegate_task), workers read_file, list_dir, edit_file, write_file, run_command | The ablation of decision 9. In `role` the orchestrator cannot edit, so it must delegate; workers use run_command for tests. |
| 32 | 2026-10-27 | Worker infrastructure errors cancel the run and are rethrown, so the run is recorded as `error` and retried | Otherwise `AgentLoop` would turn the exception into a tool result and an API outage would count as a failed attempt (decision 21). |
| 33 | 2026-10-27 | Topology prompts are two short addenda appended to the shared system prompt; their hash and the config variant (`workers=N;exposure=...`) go into the manifest | The base prompt stays identical for every config; only the role instructions differ. |
| 34 | 2026-11-01 | Conversation caching: a third cache breakpoint on the last message block (`cacheConversation`, default on), identical for every config | Without it the whole history is re-billed as fresh input every turn, which would dominate cost and hide the effect being measured. Same setting for all systems. Prices unverified (see caveats). |
| 35 | 2026-11-01 | Token attribution by source (Sys, Def, Call, Res, Text); MCP layer = Def + Call + Res; each call's cost is split by prompt position (cache-read tokens cover the earliest tokens, then cache writes, then uncached input); definitions measured once per tool set with the free token-counting endpoint; reconciled with API usage (2% tolerance) | RQ2 needs a cost share per component. Attribution is an estimate by construction; the reconciliation tolerance is reported, not hidden. |
| 36 | 2026-11-01 | Config D (coder-reviewer): reviewer sees the diff (capped 20000 chars) and may run tests, at most 3 rounds, coder continues its own history with the reviewer's feedback (`AgentLoop.ContinueAsync`) | Same loop and budget as every config. `MaxRounds = 3` is a placeholder until the pilot. |
| 37 | 2026-11-01 | Config E (sequential planner -> coder -> tester): structured hand-offs capped at 4000 chars; planner may use `run_command`; a failed test report gives the coder exactly one fix pass | Keeps E bounded and comparable to D. Tool access per role is part of the topology, not of the model. |
| 38 | 2026-11-01 | Parallel-fraction labeling: connected components of gold-patch hunks (hunks of one file, plus files linked by references), `p = 1 - max(s_i) / sum(s_i)`; label `parallel` if at least 2 components and `p >= theta`, theta = 0.4 (proposed, fixed before any results) | Replaces the earlier "two files in separate hunks" rule: it is continuous, so the thesis can regress cost on `p` as well as compare two groups. Context-only lines are ignored (fix in `TaskLabeler.Parse`). |
| 39 | 2026-11-01 | Stratified task selection (`TaskSelector.SelectStratified`, `--parallel-n`) | Plain random sampling of SWE-bench Verified would give almost no parallel tasks, and RQ3 would have no power. Stratification is declared in the report. |
| 40 | 2026-11-01 | Synthetic suite: 10 hand-written Python tasks (`tasks/synthetic`), each with `repo/`, `hidden_tests/`, a reference `solution/`; own image `mamcp-synth` (python + git, no network), own evaluator (`unittest` on hidden tests, empty patch = unresolved) | A cheap sanity check for RQ3 with known structure, runnable without the 30 GiB of SWE-bench images. Too small for statistics; used for direction only. |
| 41 | 2026-11-01 | MCP SDK `ModelContextProtocol` pinned to `0.4.0-preview.3` in `src/Mcp.Server` and `src/Agents.Mcp` | Preview API: the version is fixed so a restore cannot change behaviour mid-experiment. Not compiled in the planning sandbox (no NuGet); if the restore or build fails on the dev machine, change the version in both csproj files together. |
| 42 | 2026-11-01 | MCP server uses low-level list/call handlers and advertises `ToolCatalog` verbatim; it wraps the same `ContainerToolHost` as config A, over stdio, logs to stderr only; started as `dotnet Mcp.Server.dll --spec <base64>` | Hard rule: same tools, same behaviour, only the transport differs. Base64 spec avoids shell-quoting damage to the conda prelude. |
| 43 | 2026-11-01 | One MCP server process and one client per agent (hub with N workers = N+1 servers); hosts are tracked and closed by the orchestrator when the run ends | This is the mechanism behind H2 (each agent loads its own definitions). Process start and stdio latency are part of the MCP cost and are not hidden. |
| 44 | 2026-11-01 | Transports: A = direct, B = single agent over MCP, C/D/E = MCP by default, `--transport direct` as a control; the transport is recorded in the manifest variant | Separates the topology effect from the MCP effect (control runs of C on direct tools, if the pilot allows). |
| 45 | 2026-11-01 | `mcp-check` command: a free, Docker-less equivalence check of the MCP server against the direct host (definitions and results for success and error calls) | Verifies the hard rule before any paid run. Needs bash. |
| 46 | 2026-11-01 | Results UI is a read-only local page served by the Runner (`ui`), embedded in `Agents.Core`, plain HTML/JS/SVG, no packages, 127.0.0.1 only; `demo-data` writes clearly marked FAKE runs (`model = demo-fake`) | Works offline on the PC and needs no NuGet. The demo data lets the layout be checked before any paid run, and cannot be mistaken for results because of the banner and the model name. |
